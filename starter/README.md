# Граф денег: от Parquet до готового результата

Один запуск читает три Parquet, проверяет входные данные, рассчитывает роли,
кластеры и приоритет, затем публикует проверенные CSV и JSON. Методика и ограничения
гипотез описаны в [METHODOLOGY.md](METHODOLOGY.md).

## Установка и запуск

Команды ниже выполняются **из корня проекта**, где находятся `data/` и `starter/`.
Нужен CPython **3.14**; `.python-version` сам Python не устанавливает.

```bash
python3.14 -m venv .venv
.venv/bin/python -m pip install -r starter/requirements.txt
.venv/bin/python -m pip check
.venv/bin/python starter/starter.py --data data --out starter/out
```

Все прямые и транзитивные зависимости закреплены в `requirements.txt`.
Проверка установки в новом окружении: [CLEAN_INSTALL.md](CLEAN_INSTALL.md).
Пути `.venv/bin/python` и `../.venv/bin/python` зависят от текущей папки.
Чтобы не перепутать их, активируйте окружение из корня проекта:

```bash
source .venv/bin/activate
cd starter
python starter.py --data ../data --out ./out
```

**Все последующие команды выполняются из `starter/` с активированным окружением.**
Дополнительный профиль кейса проверяет период 1–31 июля 2026 года и минимум
5 000 KZT на операцию:

```bash
python starter.py --data ../data --out ./out --profile hackalem-july-2026
```

Без `--profile` действует общий контракт: положительная сумма от 1 тиына,
корректная дата без ограничения месяца, глубина до 4. Глубина в обоих профилях
обязательно совпадает с кратчайшим направленным расстоянием от seed.

## Результат

`out` указывает на версию с пятью файлами:

| Файл | Содержание |
|---|---|
| `nodes_roles.csv` | Все клиенты, роли, оценки, признаки и объяснения |
| `clusters.csv` | Состав, обороты и гипотезы кластеров |
| `top_nodes.csv` | Топ-20 с основаниями приоритета |
| `graph.json` | Граф и те же признаки клиентов; строковые ID |
| `manifest.json` | Версия схемы, конфигурация, SHA-256 входов и результатов |

На текущем наборе: **2 248 клиентов, 3 119 рёбер, 4 840 операций,
89 связных кластеров, 20 строк топа**. Посредничество точное, по всем 2 248
источникам. Медиана полного процесса на проверенной машине — около 2,3 секунды;
[замеры](BENCHMARK.md) отдельно показывают время импортов, анализа и публикации.

Каждый комплект сначала полностью записывается и проверяется во временной версии.
Затем ссылка `out` атомарно переключается на него. Сбой до переключения сохраняет
предыдущий результат. Старые версии остаются рядом с `out`.

Совпадающие и вложенные `--data` / `--out`, в том числе через символические ссылки,
запрещены **до расчёта**. Выход не может заменять каталог исходного кода или его
родителя. Существующая папка принимается только как распознанный комплект результатов;
произвольная папка, даже пустая, не мигрируется. Для нового результата задайте
ещё не существующий путь.

Проверка сохранённого комплекта ничего не записывает:

```bash
python starter.py validate --data ../data --out ./out
# Совместимая прежняя форма:
python starter.py --data ../data --validate-output ./out
```

Проверяются CSV, соответствие узлов и рёбер JSON, суммы, роли, кластеры, оценки и
хеши файлов. Старые CSV без JSON/манифеста остаются читаемыми; присутствующий JSON
обязательно проверяется. Код завершения: 0 при успехе, 1 при ошибке данных или
публикации. `--debug` показывает traceback ожидаемых ошибок.

Для переноса создайте обычную папку без ссылок:

```bash
python starter.py export --source ./out --destination ./portable-result
```

Назначение должно отсутствовать; исходные Parquet не нужны для экспорта нового
комплекта с манифестом. Для чтения нескольких файлов при параллельной публикации
используйте `storage.snapshot_directory()` / `validate_bundle()`: они фиксируют
открытый дескриптор каталога, включая миграцию старой обычной папки. Одного
`Path.resolve()` в случае такой миграции недостаточно.

## Точность и интерпретация

- ID проверяются как int64; пары рёбер и клиенты уникальны, концы рёбер существуют.
- Суммы операций, агрегатов, FIFO и денежных условий роли — целые **тиыны**.
  Например, граница 35% проверяется как `20 * out_tiyn <= 7 * in_tiyn`.
  KZT и дробные доли остаются полями представления; центральности используют float.
- Multi-source BFS проверяет фактическую минимальную глубину каждого клиента.
  Недостижимый от seed клиент отклоняется; изолированный seed допустим.
  `edges.depth` — метаданные обхода в допустимом диапазоне, не замена расстоянию узла.
- Все пары, суммы и количества в `edges` сверяются с `transactions` без денежного
  допуска. Одинаковые строки операций не удаляются: без ID операции это могут быть
  разные переводы. Входные производные столбцы денег/дат пересчитываются.
- Самопереводы сохраняются в исходном графе, JSON и обороте кластера один раз.
  Внешние суммы, степени, центральности, FIFO, роли и приоритет их исключают.
  Только самопереводы дают `n_peers=0` и приоритет 0; отдельные поля
  `self_transfer_tiyn`, `self_transfer_kzt`, `self_transfer_n_tx` сохраняют их объём.
- Louvain выполняется на проекции с суммированием встречных потоков. Несвязное
  сообщество разбивается на компоненты **до** расчёта зависимых признаков и ролей.
- FIFO за предыдущие 1–7 дней расходует каждое поступление один раз. Покрытие
  поступлением того же дня отмечается как неопределённое и не поддерживает транзит.
- `observation_completeness` отражает ограничения выборки. Для потоковых ролей seed
  оценка ограничена 0,65; `role_score_uncapped` и `role_score_cap` показывают поправку.
  Это поддержка эвристики, а не вероятность или подтверждение движения тех же денег.
- Приоритет независим от роли и её уверенности. Колонки `priority_*` показывают
  вклад каждого из пяти признаков; `role_facts` хранит факты для подробного объяснения.

Старый признак наличия любого предшествующего поступления не участвует в решении
о транзите. По умолчанию он не считается и колонки `temporal_out_share` нет:

```bash
python starter.py --data ../data --out ./diagnostic-result --diagnostics
```

Диагностика добавляет только этот признак. Основные роли, кластеры, оценки и топ
совпадают с обычным режимом.

## Форматы и браузер

Обязательные столбцы сохранены:

- `nodes_roles.csv`: `gid`, `role`, `role_score`, `cluster_id`, `priority_score`, `evidence`.
- `clusters.csv`: `cluster_id`, `n_nodes`, `n_seed`, `sum_kzt_internal`, `top_gids`, `hypothesis`.
- `top_nodes.csv`: `rank`, `gid`, `role`, `priority_score`, `why`.

Роли: `consolidator`, `transit`, `distributor`, `terminal`, `coordinator`, `peripheral`.
Дополнительные поля включают точные суммы `*_tiyn`, доли покрытия, режим
посредничества, полноту наблюдения, факты и вклады приоритета. `top_gids` —
JSON-массив строковых ID участников кластера. `evidence` — до 200 символов.

В CSV идентификаторы записаны целыми десятичными числами, в JSON `gid`, `src`, `dst`
— **строки**: они превышают точность JavaScript Number. Не используйте для них
`Number`, `parseInt` или float. При импорте CSV в браузер или Excel сразу задавайте
тип «текст», например `pd.read_csv(path, dtype={"gid": "string"})`.

Текущая схема JSON/манифеста — **3**. Основной пайплайн публикует только проверенный
комплект с `analysis_status="complete"`. Отдельный учебный `write_graph_json()`
помечает экспорт одних признаков как `features_only` и не заменяет проверку комплекта. Пропуски представлены `null`; NaN/Infinity и повторяющиеся
ключи JSON отклоняются. `role_facts` — JSON-строка в CSV и объект в `graph.json`.

## Границы модулей и API

| Модуль | Ответственность |
|---|---|
| `starter.py`, `cli.py` | Точка входа, совместимые экспорты, аргументы и сообщения |
| `contracts.py` | Неизменяемая конфигурация, Dataset, RuleDecision, AnalysisResult |
| `input_contracts.py`, `validation.py` | BFS, профиль данных, схемы и согласованность таблиц |
| `pipeline.py`, `analysis.py` | Подготовка данных и последовательность чистых расчётов |
| `features.py`, `temporal.py` | Внешние структурные признаки и денежное сопоставление |
| `communities.py` | Проекция, стратегия кластеризации, связность, сводки |
| `rules.py` | Упорядоченные правила, структурированные факты, отдельный renderer |
| `ranking.py` | Вклады приоритета, топ и объяснение ранга |
| `storage.py`, `output_store.py` | CSV/JSON, проверка комплекта, снимок чтения, публикация |
| `teaching.py` | Учебные шаблоны и альтернативные расстояния; вне основного запуска |

Предпочтительный API передаёт на сохранение единый результат:

```python
from pathlib import Path
from contracts import AnalysisConfig, CASE_PROFILE
from pipeline import load_dataset, run_analysis
from storage import save_result

config = AnalysisConfig(input_profile=CASE_PROFILE)
dataset, hashes = load_dataset(Path("../data"), config)
result = run_analysis(dataset, config, hashes)
save_result(result, Path("result"))
```

Для собственных DataFrame сначала вызывайте `prepare_dataset(edges, nodes, tx, config)`;
низкоуровневые расчётные функции ожидают подготовленные данные. CLI дополнительно
защищает отношения файловых путей. `AnalysisResult` объединяет граф и таблицы;
содержимое изменяемых DataFrame повторно проверяется непосредственно при сохранении.
Совместимый `starter.write_outputs(roles, clusters, top, nodes, edges, path, graph=G)`
создаёт такой результат и проходит тот же полный контроль. Внутренние эвристики
можно сравнивать через передаваемый `cluster_strategy`, не копируя пайплайн.

## Проверки и эксперименты

```bash
python -B -m unittest discover -s tests -v
python -B -O -m unittest discover -s tests
python experiments/audit_acceptance.py --data ../data --output experiments/audit-after.json
```

97 тестов покрывают граничные суммы ±1 тиын, большие целые без переполнения,
случайное разбиение и перестановку сумм, неверные глубины, FIFO, самопереводы,
связность сообществ, подмену JSON, опасные пути и ошибки/гонки публикации.
Проверки не основаны на `assert`, поэтому остаются активными с `python -O`.
