# Стартовый код — кейс «Граф денег»

Код загружает Parquet, проверяет согласованность, строит направленный граф всех
клиентов, считает базовые признаки и создаёт шаблоны для дальнейшей аналитики.
Присвоение ролей, кластеризация, рейтинг и интерфейс пока не реализованы.
Шаблоны намеренно не проходят строгую проверку готового решения.

## Окружение и запуск

Проверенное окружение: CPython **3.14.0**, macOS arm64. Версия Python указана в
`.python-version`; все прямые и транзитивные Python-зависимости закреплены в
`requirements.txt`, включая SciPy для PageRank. Сам файл `.python-version`
не устанавливает Python. На другой ОС нужно отдельно проверить доступность
колёс зависимостей; воспроизводимость на иных платформах не проверена.

Из папки `starter/`:

```bash
python3.14 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip check
.venv/bin/python starter.py --data ../data --out ./out
```

Для уже существующего окружения проекта:

```bash
../.venv/bin/python starter.py --data ../data --out ./out
```

Результат: три **шаблонных** CSV (`nodes_roles.csv`, `clusters.csv`,
`top_nodes.csv`) и `graph.json` с исходным графом и базовыми признаками.
`analysis_status` в JSON равен `features_only`; вычисленных ролей в нём нет.
Не используйте папку с готовыми результатами как `--out` для создания шаблонов:
файлы с одинаковыми именами перезаписываются.

## Проверки исходных данных

`sanity_check()` вызывает `validate_inputs()` из `validation.py`. Проверяются:

- наличие обязательных полей и отсутствие пропусков;
- целочисленные идентификаторы int64, уникальность клиентов и пар рёбер;
- существование всех отправителей и получателей в `nodes`;
- глубина 0–4 у клиентов, 1–4 у рёбер, согласованность `is_seed` с глубиной 0;
- положительные конечные суммы, не более двух знаков после запятой;
- положительное целое `n_tx`, корректные даты;
- точное совпадение пар, сумм и количества операций между `edges` и `transactions`.

Деньги для проверки переводятся в целые тиыны через `Decimal`, поэтому расхождение
на 0,01 KZT обнаруживается и при больших оборотах. Относительный допуск не применяется.
Повторные строки транзакций **не удаляются**: без ID операции они могут представлять
разные реальные переводы. Проверки используют исключения, а не `assert`, и работают
также при запуске Python с `-O`.

`build_graph(edges, nodes)` добавляет всех клиентов до добавления рёбер. На исходном
датасете граф содержит **2 248 вершин**, включая **19 изолированных**, и **35**
слабосвязных компонент. Число 16 относится к компонентам без изолированных клиентов.
PageRank теперь рассчитывается по всему графу; у изолированных вершин его значение
положительно из-за телепортации и не является свидетельством финансовой активности.

## Базовые признаки

| Колонка | Смысл |
|---|---|
| `in_deg` / `out_deg` | Количество разных отправителей / получателей |
| `in_kzt` / `out_kzt` | Наблюдаемые входящие / исходящие суммы в KZT |
| `in_tx` / `out_tx` | Количество входящих / исходящих операций |
| `pagerank` | PageRank направленного графа, вес — сумма переводов |
| `pass_through` | Отношение наблюдаемых исходящих сумм к входящим; NaN при отсутствии входящих |
| `truncated_by_depth` | Глубина 4 и отсутствие исходящих рёбер |
| `depth`, `is_seed` | Минимальное колено и признак исходного клиента |

`pass_through` не доказывает транзит тех же денег: неизвестны начальные остатки,
внешние поступления и операции вне периода. Это ограничение касается всех клиентов,
особенно seed. Узлы на четвёртом колене нельзя автоматически считать конечными
получателями. Даты позволяют проверить последовательность переводов, но порядок
операций внутри одного дня неизвестен.

## Идентификаторы и браузер

В Python и обязательных CSV `gid` остаётся int64, как требует ТЗ. На границе с
JavaScript **все** `gid`, `src`, `dst` передаются строками: они превышают
`Number.MAX_SAFE_INTEGER`. Не преобразуйте их через `Number`, `parseInt` или float.

```json
{
  "schema_version": 1,
  "analysis_status": "features_only",
  "nodes": [{"gid": "100000003684369100", "pass_through": null}],
  "edges": [{"src": "100000003684369100", "dst": "100000002398779100", "sum_kzt": 10000.0}]
}
```

Это сокращённый пример: реальные записи узлов содержат все базовые признаки.
`write_graph_json()` создаёт стандартный JSON: отсутствующие числовые значения
записываются как `null`, а не `NaN`. Строковые ID нужно сохранять и в поиске, и в
библиотеке визуализации графа.

При чтении CSV для браузера задавайте `gid` как текст сразу, до автоопределения
числового типа. Например, `pd.read_csv(path, dtype={"gid": "string"})`.
Обычное открытие CSV в Excel также может округлить длинные ID; импортируйте эту
колонку как текст. Проверка готовых CSV читает ID как текст и отклоняет десятичную
и экспоненциальную запись вместо попытки восстановить уже потерянную точность.

## Формат готового результата

Обязательные поля:

- `nodes_roles.csv`: `gid`, `role`, `role_score`, `cluster_id`, `priority_score`, `evidence`.
- `clusters.csv`: `cluster_id`, `n_nodes`, `n_seed`, `sum_kzt_internal`, `top_gids`, `hypothesis`.
- `top_nodes.csv`: `rank`, `gid`, `role`, `priority_score`, `why`.

Дополнительные колонки допускаются. Роли: `consolidator`, `transit`, `distributor`,
`terminal`, `coordinator`, `peripheral`. Идентификаторы кластеров — неотрицательные
целые. `top_gids` — JSON-массив **строковых** ID участников соответствующего кластера,
например `["100000003684369100"]`; при записи через pandas поле экранируется по правилам CSV.

## Строгая проверка готовых CSV

```bash
../.venv/bin/python starter.py --data ../data --validate-output ./result
```

Команда читает исходные данные и CSV, ничего не записывает и возвращает код 1 при
ошибке. Успешная проверка возвращает код 0. Проверяются:

- каждый входной клиент представлен ровно один раз: для текущего набора 2 248 строк;
- допустимая роль, конечные числовые оценки в диапазоне 0–1;
- непустое `evidence` до 200 символов, содержащее числовое основание;
- все кластеры существуют, нет дублирующихся и неиспользуемых ID кластеров;
- размеры, число seed и внутренние обороты кластеров совпадают с данными;
- непустые гипотезы и корректные `top_gids`, принадлежащие кластеру;
- минимум 20 уникальных известных клиентов в топе;
- ранги 1..N в порядке строк, приоритеты по убыванию;
- роли и оценки в топе совпадают с основной таблицей;
- в топ не попали менее приоритетные клиенты вместо более приоритетных;
- непустое `why` с числами. При одинаковых оценках любой порядок допустим.

Проверка подтверждает формальную согласованность, но не истинность гипотез или
качество формул скоринга. Число клиентов берётся из `nodes`, не зашито в код.

После реализации аналитики используйте проверяемую запись:

```python
from pathlib import Path
from starter import write_outputs

# roles, clusters, top — уже рассчитанные DataFrame.
write_outputs(roles, clusters, top, nodes, edges, Path("result"))
```

Функция проверяет таблицы до записи и повторно проверяет сохранённые CSV.
`write_templates(features, path)` — отдельная функция для учебных заготовок.
Прежняя сигнатура `write_outputs(features, path)` заменена именно на неё.
Пустые шаблоны не следует заполнять фиктивными ролями ради прохождения проверки.

## Направления и веса

Сумма ребра имеет разный смысл в разных алгоритмах:

```python
import networkx as nx
from starter import betweenness_features

# Вес — сила связи: большая сумма увеличивает вклад ребра.
pr = nx.pagerank(G, weight="sum_kzt")

# Кратчайшие пути по числу шагов, направление сохраняется.
b_hops = betweenness_features(G, distance_mode="hops")

# Альтернативная гипотеза: более крупный поток означает меньшую дистанцию.
# На копии графа создаётся distance = 1 / sum_kzt.
b_amount = betweenness_features(G, distance_mode="inverse_amount")
```

Не передавайте `sum_kzt` как расстояние в `betweenness_centrality`: тогда большой
перевод удлинит путь. Обратная сумма также является допущением, а не доказательством
финансового маршрута. Для приближённого расчёта можно задать `sample_size` и `seed`.
Весовое посредничество использует вещественные расстояния; при почти равных путях
возможны численные эффекты. Для базового структурного анализа используйте `hops`.

Если используется неориентированная кластеризация, явно создавайте проекцию и
**суммируйте** встречные потоки, иначе один из весов может быть потерян:

```python
UG = nx.Graph()
UG.add_nodes_from(G.nodes)
for src, dst, attrs in G.edges(data=True):
    old = UG.get_edge_data(src, dst, {}).get("sum_kzt", 0.0)
    UG.add_edge(src, dst, sum_kzt=old + attrs["sum_kzt"])
communities = nx.community.louvain_communities(UG, weight="sum_kzt", seed=42)
```

Фиксированный seed делает запуск повторяемым при тех же данных, порядке и версиях;
он не доказывает устойчивость состава сообществ. Проверяйте несколько запусков.

## Тесты

Из `starter/`:

```bash
../.venv/bin/python -B -m unittest discover -s tests -v
../.venv/bin/python -B -O -m unittest discover -s tests
```

Используется стандартный `unittest`, дополнительных тестовых зависимостей нет.
Тесты покрывают несовпадение пар, сумм и количества, изолированные узлы, точность
ID, строгий JSON, ошибочные выгрузки, CSV round-trip и смысл расстояний.

## Рост до миллиона узлов

Текущая реализация рассчитана на локальный небольшой датасет. Для миллиона узлов
нужно вынести агрегацию в колоночный движок/БД, заменить объекты NetworkX компактным
графовым представлением, считать посредничество приближённо и ограничивать
визуализацию окрестностью выбранного узла. Валидацию внутренних оборотов кластеров
следует векторизовать. Это направление развития, не реализованная возможность.
